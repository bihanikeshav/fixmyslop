# Forms & Input UX

> A form is a conversation between a product and its user — every unnecessary field, vague error, and misplaced label is friction that costs completion.

## Why it matters

Forms are the primary mechanism through which users give products what they need: accounts, orders, data, configuration. Baymard Institute research across 326+ e-commerce sites found that 17% of users abandon purchases specifically because checkout forms are too long or too complex — a measurable revenue figure, not a soft UX concern. [Baymard, "Checkout Optimization: Minimize Form Fields", https://baymard.com/blog/checkout-flow-average-form-fields] Nielsen Norman Group testing showed forms following usability guidelines achieve 78% one-try submissions versus 42% in non-compliant forms. [NN/g, "Website Forms Usability: Top 10 Recommendations", https://www.nngroup.com/articles/web-form-design/] Form UX compounds across every product that has authentication, checkout, onboarding, or settings — which is almost every product.

## Core principles

**1. Every field has a cost — earn the right to ask.**
The fundamental constraint of form design is that each field imposes cognitive tax: the user must understand the question, recall or compose an answer, enter it correctly, and handle any validation failure. Luke Wroblewski, whose 2008 book *Web Form Design: Filling in the Blanks* remains the field's foundational reference, frames this as progressive disclosure: never ask for information you can infer, compute, collect later, or skip entirely. [Wroblewski, *Web Form Design*, Rosenfeld Media, 2008, book, no canonical URL; https://rosenfeldmedia.com/books/web-form-design/] The GOV.UK Design System formalises this as a **question protocol**: before building a form, list every question and justify its necessity — "what will we do with this answer?" eliminates many fields before a pixel is drawn. [GOV.UK Design System, "Question pages", https://design-system.service.gov.uk/patterns/question-pages/] Baymard found the average e-commerce checkout contains 11.3 fields; optimal is 7–8. [Baymard, "Checkout Optimization: Minimize Form Fields", https://baymard.com/blog/checkout-flow-average-form-fields]

**2. Single-column layouts respect the natural reading path.**
Multi-column forms impose a branching scan path: the user must decide whether columns are independent, sequential, or parallel — a decision that costs time and produces errors. NN/g's top-10 form recommendations state flatly: "Present fields in a single column layout." [NN/g, "Website Forms Usability: Top 10 Recommendations", https://www.nngroup.com/articles/web-form-design/] The narrow exception — logically inseparable fields like City / State / ZIP that are short and always used together — is valid precisely because the relationship is semantically unambiguous and the fields are too small to stand alone. Wroblewski's research on form structure reinforces this: vertical momentum keeps users in a predictable flow that mobile layouts already enforce. [Wroblewski, *Web Form Design*, book, no canonical URL]

**3. Top-aligned labels minimise eye fixations.**
The placement of a label relative to its input field determines how many distinct eye movements a user must make to process each field. Matteo Penzo's eye-tracking study, summarised by Wroblewski, found that labels placed directly above their field produced the shortest saccade times — approximately 50ms — because "users can capture both elements with a single eye movement." Right-aligned labels to the left of the field improved over left-aligned labels (reducing fixations by roughly half) but still required a horizontal scan. Left-aligned labels, the most visually tidy for designers, produced the highest cognitive load: saccade times of ~500ms and significantly more fixations. [Wroblewski, "Eyetracking Web Forms", https://www.lukew.com/ff/entry.asp?374=; Penzo, "Label Placement in Forms", UXmatters, https://www.uxmatters.com/mt/archives/2006/07/label-placement-in-forms.php] Top-aligned labels also accommodate longer label text without truncation — important for accessibility. Adam Silver's *Form Design Patterns* echoes this: "Placing a label right over its input field permitted users to capture both elements with a single eye movement." [Silver, *Form Design Patterns*, Smashing Magazine, 2018, book, no canonical URL; excerpt at https://www.smashingmagazine.com/2018/10/form-design-patterns-excerpt-a-registration-form/]

**4. Placeholders cannot substitute for labels.**
Placeholder text disappears the moment a user begins typing. NN/g identified seven distinct usability failures this creates: short-term memory burden (users forget instructions mid-entry, especially after interruptions), inability to verify entries before submission without deleting them, difficulty correcting errors (user must re-delete input to re-read the prompt), confusion with pre-filled values causing skipped fields, and poor accessibility — the default grey contrast fails WCAG minimum ratios and screen readers announce placeholder content inconsistently. [NN/g, "Placeholders in Form Fields Are Harmful", https://www.nngroup.com/articles/form-design-placeholders/] Baymard's mobile research documents users deleting their entire input just to see an inline label again, and an explicit case from Fandango testing where location validation errors became unresolvable because the "City, State OR Zip Code" inline label was no longer visible. [Baymard, "Mobile Form Usability: Never Use Inline Labels", https://baymard.com/blog/mobile-forms-avoid-inline-labels] Floating labels (labels that begin as placeholder text and animate to a top position on focus) mitigate memory burden but retain some contrast and discoverability problems; they are a last resort, not a best practice.

**5. Inline validation times matter — validate on blur, not keystroke.**
Live inline validation — showing success or error states as the user fills the form rather than at submission — demonstrably reduces errors and completion time. Wroblewski describes its benefit: "confirmation that an appropriate answer was given, suggestions for valid answers, and real-time updates designed to help people stay within necessary limits." [Wroblewski, *Web Form Design*, book, no canonical URL] The critical timing question is *when* to trigger validation. Baymard's usability testing found that validating while a user is still typing ("premature validation") produces hostile false negatives: "Why are you telling me my email address is wrong, I haven't had a chance to fill it out yet?" The correct trigger is `onblur` — when the user leaves the field. [Baymard, "Usability Testing of Inline Form Validation", https://baymard.com/blog/inline-form-validation] Exception: fixed-length inputs like ZIP codes or credit card numbers can validate once the correct character count is reached. Error states should clear on a keystroke level — the moment the input becomes valid, the error disappears, not when the user tabs away again.

**6. Error messages must be specific, proximate, and instructive.**
Vague errors ("invalid input", "something went wrong") make users guess. Effective error messages do three things: identify the specific problem, locate themselves immediately adjacent to the offending field (not only in a banner at the top), and tell the user exactly how to fix it. The GOV.UK Design System's wording guidance prohibits technical jargon, weak language ("please", "sorry"), and vague terms ("valid", "invalid") — the pattern is "Describe what has happened and tell them how to fix it." The system also requires a hidden "Error:" prefix for screen readers via `govuk-visually-hidden` and an error summary at page top for multi-error states, using `role="alert"` and automatic focus management. [GOV.UK Design System, "Error message", https://design-system.service.gov.uk/components/error-message/; "Error summary", https://design-system.service.gov.uk/components/error-summary/] NN/g's top-10 recommendations reinforce: "Preserve erroneous input so users can correct it" — resetting a field on error forces the user to retype everything. [NN/g, "Website Forms Usability: Top 10 Recommendations", https://www.nngroup.com/articles/web-form-design/]

**7. Field length and input type should match expected input.**
A field's visual width sets an implicit expectation about the length of the expected answer. A full-width field for a two-digit year code creates confusion; a narrow field for a mailing address forces horizontal scrolling. NN/g recommends matching field size to expected content. [NN/g, "Website Forms Usability: Top 10 Recommendations", https://www.nngroup.com/articles/web-form-design/] Input type drives the mobile keyboard: `type="email"` surfaces `@` without switching, `type="tel"` shows a numeric keypad, `type="number"` often behaves badly for non-numeric purposes. The `inputmode` attribute decouples keyboard hint from semantic type: `inputmode="numeric"` on a `type="text"` field (useful for OTPs, CVV codes) surfaces digits without the browser's built-in number spinner or formatting. The `autocomplete` attribute — with over 50 standardised token values — enables browser and password-manager autofill for names, addresses, credit cards, and one-time codes. Together, `type`, `inputmode`, and `autocomplete` are the three attributes that make mobile form entry tolerable. [Wroblewski / makandracards, "Better HTML forms: use type, inputmode, enterkeyhint and autocomplete", https://makandracards.com/makandra/589282-better-html-forms-type-inputmode-enterkeyhint-autocomplete]

**8. Mark optional fields — not required fields — with "(optional)".**
When most fields in a form are required (the common case), marking required fields with asterisks creates visual noise without adding information. The more useful signal is to mark the *exceptions* — optional fields — clearly in their label. The GOV.UK Design System codifies this: "Mark optional fields with '(optional)' — never use asterisks for mandatory fields." [GOV.UK Design System, "Question pages", https://design-system.service.gov.uk/patterns/question-pages/] NN/g recommends limiting optional fields to one or two at most and eliminating them where possible. [NN/g, "Website Forms Usability: Top 10 Recommendations", https://www.nngroup.com/articles/web-form-design/] The best practice is to question protocol your way to a form that is almost entirely required fields, then clearly flag the rare exceptions.

**9. Smart defaults reduce decision load.**
Pre-selecting the most common answer, pre-filling values the system already knows, and detecting context (timezone from the browser, country from the IP address) eliminates questions the user should never have to answer. The principle is that it is better UX to "have preloaded data in form fields and ask users to validate it, than to ask them to type all the data again." [Shopify Partners Blog, "How to Use Smart Defaults to Reduce Cognitive Load", https://www.shopify.com/partners/blog/cognitive-load] Defaults carry ethical weight: pre-selecting the more privacy-invasive or more expensive option is a dark pattern. A default must benefit the user, not the business. Today's date, the user's existing address on repeat purchase, and detected locale are legitimate defaults; pre-checked marketing opt-ins and upsells are not.

**10. Group related fields and use whitespace to encode proximity.**
Gestalt's Law of Proximity explains that items placed near each other appear to belong together. NN/g's research on form white space showed that grouping related fields under a shared heading or within visual proximity — and placing each label closer to its own field than to adjacent fields — significantly aids comprehension. [NN/g, "Group Form Elements Effectively Using White Space", https://www.nngroup.com/articles/form-design-white-space/] For long forms, divide fields into named sections ("Personal details", "Payment", "Delivery") so users can orient themselves and predict how much remains. "Even the slightest moment of hesitation when completing a form can significantly hurt the form's response rate," per NN/g — visual grouping removes that hesitation.

**11. Multi-step forms with progress indicators reduce abandonment on complex tasks.**
Long forms presented as a single scrolling page present total length upfront, which increases perceived effort and abandonment. Breaking a complex form across steps — asking one coherent question or topic per screen — reduces apparent effort at each moment. The GOV.UK Service Manual's "one thing per page" pattern states: "Start by splitting the form across multiple pages with each page containing just one thing... [this] helps users understand what you're asking them to do, focus on the specific question and its answer, find their way through an unfamiliar process." [GOV.UK, "Structuring forms", https://www.gov.uk/service-manual/design/form-structure] Research aggregated from multiple conversion studies finds multi-step forms achieve higher completion rates than single-page equivalents for complex data collection, with progress indicators reducing abandonment further by making the endpoint visible. Optimal depth is 3–5 steps; beyond 6, completion rates decline. The primary action button on each step should say "Continue", not "Next" (GOV.UK convention) — or be contextually labelled (e.g., "Create account" on the final step), never "Submit" alone.

**12. Accessible forms require correct semantics, not just visual design.**
Every input must have a programmatically associated `<label>` with a matching `for`/`id` pair — not an `aria-label` substitute, not a nearby `<span>`, not a placeholder. This satisfies WCAG 1.3.1 (Info and Relationships) and WCAG 3.3.2 (Labels or Instructions). Error messages must be associated via `aria-describedby` pointing from the input to the error element, and `aria-invalid="true"` must be set on the invalid input so screen readers announce the error state when the field receives focus. [WCAG 2.2, "3.3.1 Error Identification (Level A)"; GOV.UK Design System, "Error message", https://design-system.service.gov.uk/components/error-message/] Error states must never rely on colour alone — a red border without an icon or text fails WCAG 1.4.1 (Use of Colour). Adam Silver's accessibility framework for forms identifies four user needs: visual (content easy to see), auditory (screen reader compatible), motor (large hit areas through `<label>` elements), and cognitive (plain language). [Silver, *Form Design Patterns*, book, no canonical URL] Focus management matters: after form submission with errors, keyboard focus should move to the error summary or the first erroneous field.

## How to apply (web UI)

- **DO** place labels above their fields in every mobile-first or general-purpose form. Reserve left-aligned labels only for dense internal tools where horizontal space is plentiful and label text is consistently short.
- **DO** use a single-column layout. Exceptions (City/State/ZIP) must be semantically inseparable, short, and used together.
- **DO** associate every `<input>`, `<select>`, and `<textarea>` with a visible `<label for="...">`. Never substitute placeholder text or `aria-label` alone.
- **DO** set `autocomplete` tokens on all personal data fields (`name`, `email`, `tel`, `street-address`, `postal-code`, `cc-number`, `one-time-code`, etc.).
- **DO** use `inputmode="numeric"` for PIN, OTP, and CVV fields (keeps `type="text"` semantics with numeric keyboard).
- **DO** trigger field validation `onblur` — when focus leaves the field. Clear error state on keystroke once the value is valid.
- **DO** write error messages as: [what went wrong] + [how to fix it]. "Enter your email address in the format name@example.com" not "Invalid email".
- **DO** place error messages between the label and the field, not only in a banner.
- **DO** set `aria-invalid="true"` and `aria-describedby` pointing to the error element on any invalid input.
- **DO** mark optional fields with "(optional)" in the label text; remove asterisks.
- **DO** pre-fill fields with known data (logged-in user's address, detected locale) and ask for confirmation rather than re-entry.
- **DO** match field width to expected input length (a 2-digit year field should not span full column width).
- **AVOID** validating while the user is still typing — premature validation causes false positives and hostile UX.
- **AVOID** resetting field values after a validation error — force the user to correct, never retype.
- **AVOID** placing more than two optional fields in a form; eliminate them by question protocol instead.

## Anti-patterns

**Placeholder-as-label.** Using `placeholder` as the sole labelling mechanism is the most common and most damaging form anti-pattern. Labels must remain visible at all times; placeholders vanish on first keystroke. Documented consequences: users forget field intent during entry, cannot verify inputs before submission, delete correct entries to re-read prompts, and screen readers may not announce placeholder content at all. [NN/g, "Placeholders in Form Fields Are Harmful", https://www.nngroup.com/articles/form-design-placeholders/; Baymard, "Mobile Form Usability: Never Use Inline Labels", https://baymard.com/blog/mobile-forms-avoid-inline-labels]

**Validating on keystroke.** Triggering error states while a user is actively typing produces false negatives on every partially-complete value. The message "invalid email" appearing after typing "jo" is not helpful — it is hostile. Baymard user testing produced direct quotes expressing frustration with premature validation; it erodes trust and increases abandonment. [Baymard, "Usability Testing of Inline Form Validation", https://baymard.com/blog/inline-form-validation]

**Vague error messages.** "Something went wrong", "invalid input", and "please try again" tell the user nothing actionable. Error messages that fail to specify what is wrong, where the problem is, and what valid input looks like force users to guess repeatedly or abandon. GOV.UK's guidance explicitly bans "valid", "invalid", and technical jargon from error copy. [GOV.UK Design System, "Error message", https://design-system.service.gov.uk/components/error-message/]

**Multi-column form layout.** Side-by-side fields — other than genuinely inseparable pairs — disrupt the natural top-to-bottom completion path and create ambiguity about order. Multi-column layouts also fail disproportionately on mobile, where narrow viewports force reflow in ways that break the intended grouping. [NN/g, "Website Forms Usability: Top 10 Recommendations", https://www.nngroup.com/articles/web-form-design/]

**Resetting fields on submission error.** Clearing field values when a form fails validation forces users to reconstruct their answers from scratch. NN/g identifies this as a critical failure: "Preserve erroneous input so users can correct it." [NN/g, "Website Forms Usability: Top 10 Recommendations", https://www.nngroup.com/articles/web-form-design/] GOV.UK's error message guidance adds: "Do not clear any form fields when showing the error message component." [GOV.UK Design System, "Error message", https://design-system.service.gov.uk/components/error-message/]

**Collecting fields you do not need.** Asking for phone numbers "in case we need to contact you", company name on a B2C checkout, or "how did you hear about us?" without a clear operational use adds friction for business reasons that do not serve the user. Baymard's checkout research found these unnecessary fields among the highest correlates of abandonment. [Baymard, "Checkout Optimization: Minimize Form Fields", https://baymard.com/blog/checkout-flow-average-form-fields] Every field removed is a conversion problem solved without any UI work.

**Relying on colour alone for error states.** A red border is insufficient: users with colour-blindness cannot perceive it, and screen readers do not read CSS. Error state requires at least one of: an error icon, visible error text, `aria-invalid="true"`, and `aria-describedby` linking the input to the error message. [WCAG 2.2, "1.4.1 Use of Colour (Level A)"; GOV.UK Design System, "Error message", https://design-system.service.gov.uk/components/error-message/]
